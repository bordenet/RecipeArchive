# Monitoring Runbook for RecipeArchive

## Overview
This document outlines the procedures for responding to alerts generated by the CloudWatch monitoring system for the RecipeArchive application. The goal is to quickly diagnose and resolve issues related to recipe parsing, normalization, and overall system health.

## Alerting Channels
All critical alerts are routed to the `RecipeArchive Production Alerts` SNS topic, which currently sends email notifications to `your-email@example.com`.

## Alarms and Response Procedures

### 1. HighParsingFailures Alarm
- **Description**: Parser is failing frequently - check diagnostics S3 bucket.
- **Metric**: `RecipeArchive/Diagnostics` -> `ParsingFailures` (Sum, 5 minutes)
- **Threshold**: > 10 failures in 10 minutes (2 evaluation periods of 5 minutes)
- **Severity**: High
- **Response Steps**:
  1. **Acknowledge Alert**: Confirm receipt of the alert.
  2. **Check CloudWatch Dashboard**: Navigate to the `RecipeArchive-Production` dashboard in CloudWatch. Look at the "Parsing Failures by Error Type" widget to identify the predominant error types (e.g., `EMPTY_RECIPE`, `PARSE_ERROR`).
  3. **Inspect Diagnostics S3 Bucket**: Go to `s3://recipe-failed-{id}/diagnostics/` and `s3://recipe-failed-{id}/failed-parsing/`. Download a few recent `.json` diagnostic files and `.html` failed parsing files to understand the content that caused the failures.
  4. **Identify Root Cause**: 
     - If `EMPTY_RECIPE` is high: The parser is likely failing to extract any recipe data. This could be due to website layout changes or a bug in the parser logic.
     - If `PARSE_ERROR` is high: The parser is encountering structural issues or unexpected data formats.
     - If `VALIDATION_ERROR` is high: The extracted data does not conform to the expected schema.
  5. **Review Recent Deployments**: Check recent deployments of the browser extensions and the `diagnostics` lambda. A recent change might have introduced a regression.
  6. **Escalate**: If the root cause is not immediately apparent or requires code changes, escalate to the development team.
  7. **Mitigation**: If a specific website is causing a high volume of errors, consider temporarily blacklisting it in the extension (if such a feature exists) or disabling the problematic parser.

### 2. GarbageRecipes Alarm
- **Description**: Normalizer producing recipes with 0 ingredients AND 0 instructions.
- **Metric**: `RecipeArchive/Normalizer` -> `GarbageRecipes` (Sum, 15 minutes)
- **Threshold**: > 5 garbage recipes in 15 minutes (1 evaluation period of 15 minutes)
- **Severity**: High
- **Response Steps**:
  1. **Acknowledge Alert**: Confirm receipt of the alert.
  2. **Check CloudWatch Dashboard**: Navigate to the `RecipeArchive-Production` dashboard. Look at the "Recipe Quality" widget, specifically the "Garbage (0/0)" metric.
  3. **Inspect Background Normalizer Logs**: Review the CloudWatch logs for the `background-normalizer` lambda. Look for `ERROR: Recipe has 0 ingredients and 0 instructions` messages to identify the URLs of the problematic recipes.
  4. **Identify Root Cause**: 
     - The OpenAI normalization process might be failing to extract data correctly.
     - The input recipe data might already be malformed before normalization.
     - OpenAI API issues (rate limits, errors, etc.).
  5. **Review Recent Deployments**: Check recent deployments of the `background-normalizer` lambda. A recent change might have introduced a regression.
  6. **Escalate**: If the root cause is not immediately apparent or requires code changes, escalate to the development team.
  7. **Mitigation**: If the issue is with the OpenAI API, check its status page. If it's a specific recipe source, investigate why it's producing garbage data.

### 3. LambdaErrors Alarm
- **Description**: Lambda function errors detected.
- **Metric**: `AWS/Lambda` -> `Errors` (Sum, 5 minutes) for `background-normalizer`
- **Threshold**: > 3 errors in 5 minutes (1 evaluation period of 5 minutes)
- **Severity**: Medium
- **Response Steps**:
  1. **Acknowledge Alert**: Confirm receipt of the alert.
  2. **Check CloudWatch Logs**: Go to the CloudWatch logs for the `background-normalizer` lambda. Look for error messages and stack traces.
  3. **Identify Root Cause**: Determine if the errors are transient (e.g., network issues, temporary API unavailability) or persistent (e.g., code bug, misconfiguration).
  4. **Review Recent Deployments**: Check recent deployments of the `background-normalizer` lambda.
  5. **Escalate**: If it's a persistent issue, escalate to the development team.
  6. **Mitigation**: If the errors are transient, monitor the situation. If persistent, a rollback of the last deployment might be necessary.

### 4. HighDiagnosticVolume Alarm
- **Description**: Large number of diagnostic files - possible parser regression.
- **Metric**: `AWS/S3` -> `NumberOfObjects` (Average, 1 hour) for `recipe-failed-{id}` bucket with `diagnostics/` prefix
- **Threshold**: > 100 objects in 1 hour
- **Severity**: Low (Informational)
- **Response Steps**:
  1. **Acknowledge Alert**: Confirm receipt of the alert.
  2. **Check S3 Bucket**: Verify the number of objects in `s3://recipe-failed-{id}/diagnostics/`.
  3. **Investigate**: This alarm indicates a high volume of diagnostic data being written, which could mean a widespread parsing issue across many users or websites. Follow the steps for the `HighParsingFailures` alarm to investigate the nature of the failures.
  4. **Inform Development**: This is typically an informational alert, but it's good to inform the development team about the increased diagnostic volume.

## General Troubleshooting Steps
- **Check AWS Service Health Dashboard**: Verify there are no ongoing AWS service disruptions in the region.
- **Review Recent Code Changes**: Use `git log` or your CI/CD system to review recent commits to the affected services.
- **Check Dependent Services**: Ensure any external APIs or services that RecipeArchive depends on are operational.
